# Golden vectors and cross-language parity

The same scoring computation runs in four places, and all four must agree byte for byte. This
page explains how that agreement is enforced, and how to check it yourself.

## One algorithm, four ports

The canonical algorithm and every byte encoding live in one Rust crate,
[`packages/pagerank-core`](../../packages/pagerank-core/) (shared low-level primitives, such as
merkle folding and fixed-point words, live in [`packages/zk-core`](../../packages/zk-core/),
which every core crate re-exports). That single source of truth is then:

1. run as **native Rust** (tests, tooling, the prover host);
2. compiled into the **SP1 guest** ([`zk/program`](../../zk/program/)), the binary that is
   actually proven;
3. asserted against **Solidity** golden tests
   ([`test/unit/golden/`](../../test/unit/golden/)), which lock the on-chain encodings
   (params hashing, journal digest, merkle leaves);
4. ported to **TypeScript** for the browser
   ([`frontend/lib/pagerank/`](../../frontend/lib/pagerank/) and the sibling program libs),
   so the app can preview scores without a server.

The crate is written to be reproducible by construction: no floats, no non-deterministic
iteration order. That is what makes byte-level parity a meaningful target at all.

## The vectors

[`test/golden/`](../../test/golden/) holds one golden-vector file per program:
`trust-graph.json`, `hypercerts.json`, `contributions.json`. Each file is generated by the
program's Rust core (an `export_golden` example) and contains inputs plus every intermediate
and final encoding: params bytes and hash, edge leaves, merkle root, journal bytes and digest,
score blob, CID. The signer-sync program is the one exception: it reads the same attestation
feed as trust-graph, so its vectors live under the `signer` key of `trust-graph.json` rather
than in a separate file.

The Solidity suites (`TrustgraphsGoldenVectors.t.sol`, `SignerGoldenVectors.t.sol`,
`HypercertsGoldenVectors.t.sol`, `ContributionsGoldenVectors.t.sol`) and the frontend
`golden.test.ts` files all read those same JSON files and re-derive the same bytes
independently.

## How drift is caught

The parity gate regenerates the vectors from the Rust core and then requires
`git diff --exit-code test/golden/` to pass. So an encoding change that ships without
regenerated vectors in the same PR fails CI, and regenerating the vectors forces every other
port's suite to confront the change. CI runs the gate for every program on every PR touching
`packages/` or `zk/`.

## Check it yourself

The whole gate, for one program (values: `trust-graph`, `signer`, `hypercerts`,
`contributions`):

```bash
task zk:parity PROGRAM=trust-graph
```

That runs five checks in order: regenerate vectors and fail on drift, Rust tests across the
core crates, the Solidity golden suites, the frontend TypeScript golden tests, and a
guest-equals-native byte assertion that executes the real guest ELF in the SP1 executor. The
last step needs the guest ELFs built once first (`task zk:build`).

Piecewise, the same checks are:

```bash
cargo test -p pagerank-core                    # native Rust core + its vectors
forge test --match-path "test/unit/golden/*"   # Solidity golden suites
cd frontend && pnpm test                       # TypeScript ports' golden tests
task zk:execute PROGRAM=trust-graph            # guest ELF == native, byte-asserted
```

## Why this matters for verification

The proof pins the guest: the on-chain verifier accepts only the exact guest binary named by
its verification key (see [addresses and vkeys](./addresses-and-vkeys.md)). Golden vectors pin
every other port to that guest. Together they mean the score you preview in the browser, the
bytes a contract hashes, and the root a proof commits are all the same computation, and none
of them can drift from what is actually proven without CI failing first.
