offchain attestations, hypercerts, contributions, and the current cleanup program) plus
[`research/OFFCHAIN_ATTESTATIONS_ZK.md`](../research/OFFCHAIN_ATTESTATIONS_ZK.md),

and which plan section it touches. No silent divergence. Convention: the active build plan lives at
the repo root as `GOAL.md` while a program is in flight and is deleted (not archived) when done —
history lives in git and in this file. "GOAL.md" in the table below refers to whichever build plan

| 19 | 2026-07-28 | GOAL.md (proof scheduler) M3 — `submitAndClaim` as the sole payout seam, and `MerkleSnapshot`'s scope | M3's security pass (8 parallel `solidity-auditor` agents) confirmed defects that the design as written could not fix from inside the vault, so **`MerkleSnapshot` changed twice more**: it now records `checkpointRecipient[id]` on every `submitProof`, and `trigger()` refuses a checkpoint identical to the last one across BOTH lanes. `IProvingVault` also grew a standalone `claim()` and a `SubmitArgs.minPayoutUsd`. | Three findings, each defeating a headline property, and none of them addressable in `ProvingVault` alone. (a) **The seam was bypassable.** `submitProof` is permissionless, so anyone could lift a pending claim's proof out of the mempool and land it directly; the prover's `submitAndClaim` then reverted `StaleCheckpoint` and, because monotonicity is permanent, the fee became unpayable by *anyone*. The interface's headline claim ("copy a pending claim and you pay the original prover") held only for copies routed through the vault, and the cheaper copy was the one that went around it. Recording the journal's recipient makes the bounty survive the submission, so `claim()` pays it afterwards and the copier buys nothing. (b) **One proof, many checkpoints.** The journal commits the checkpoint's *contents*, not its *identity*, and two of the three shipped lane-1 seams deliberately have no `NoNewInputs` guard (`TrustAccumulatorMirror` so a quiet vouch graph cannot wedge a contributions round; `EmptyLaneAccumulator` because its lane is constant). On those, a stranger could mint an unlimited run of identical checkpoints and collect a full bounty against each. Moving the guard into `trigger()` and checking both lanes is what makes it total — `trigger()` is the only minter and the only caller that sees both lanes — and it is strictly cheaper than a fifth vkey rotation to put `checkpointId` in the journal. (c) **Every payout input was zeroable in the same block**, by front-run or by a hook re-entering from inside the forwarded `submitProof`; the checkpoint's one-shot bounty slot was consumed anyway. `minPayoutUsd` lets the prover state its price, so the community gets a reverted transaction rather than a free root. Also fixed in the same pass: the withdrawal notice debited spendable balance instantly and `cancelWithdrawal` restored it for free (a free-roots toggle, found independently by four agents); `_sizeOf`'s failed-read fallback landed on the *cheapest priced* band rather than the unpriced one, inverting the invariant its own comment asserted; `bandOf` used `max`/single-lane while the operator's cycle estimate sums both lanes, so the "same boundary" both sides test was untested for every two-lane instance; the price feed had no sanity band, so at a crashed $1/ETH a $50-capped claim withdrew 50 ETH; and `block.timestamp - updatedAt` sat in a `try` success branch where a future-dated feed would panic and block roots entirely. |

Notes that are **not** deviations, recorded for context:

- Executor-only prover commands (`execute`, `vkey`, `paramshash`) default to `SP1_PROVER=mock` in
  `taskfile/zk.yml` and `test/e2e/run.sh`: the default cpu backend eagerly allocates the ~5 GiB CPU
  prover machine these commands never use, OOM-killing small boxes/CI runners. The executor and the
  guest==native byte-assert are identical under mock; `prove` respects the caller's `SP1_PROVER`.
- M0 re-derived vkeys (ELF layout changed under the refactor; semantics didn't — golden vectors are
  byte-identical to pre-reorg). Recorded in [`PROGRAMS.md`](./PROGRAMS.md); rotation of the live stack
  is batched to M2 per GOAL.md ground rule 7.
- Contributions slot-A wiring is a **read-only mirror**, resolving CONTRIBUTION_FUNDING.md §3's
  stated open question ("whether the contrib snapshot reads the trust accumulator's existing
  checkpoints or pushes its own — two snapshots triggering one accumulator needs a look"): the
  contrib `MerkleSnapshot`'s `accumulator` is a `TrustAccumulatorMirror` whose `checkpoint()`
  READS the trust accumulator's live `(acc, leafCount)` and freezes it into the mirror's own
  checkpoint array — nothing is ever pushed into the trust accumulator, so the two instances'
  trigger cadences cannot race and the trust instance's checkpoint ids stay its own. The mirror
  deliberately has NO `NoNewInputs` guard (a quiet vouch graph must not wedge contrib round
  triggers; spam is bounded by the contrib snapshot's `epochLength` gate). The proven input
  commitment is unchanged — `acc` already commits to the full ordered edge log.
- The contributions schema strings are REGISTERED in the canonical comma-no-space form
  (`string title,bytes32 contentHash,…` — the house schema-string format every existing network
  entry uses and the config field parser consumes); `docs/contributions/INTERFACES.md` §1's
  comma-space rendering is table presentation, not wire format. The golden vectors bind schema
  UIDs as opaque placeholders, so nothing golden depends on the string spelling.
