# v0.1.0 candidate and promotion gates

The release version identifies the complete deployment and its artifact manifest. Workspace crate
versions (`0.9.3`), the root JavaScript tooling package (`0.4.0`) and standalone application/guest
versions have independent package histories. Do not infer a guest verification key from a package
version. Source commit, ELF digest and program verification key identify an immutable guest.

## Build and publish

1. Commit the complete candidate, including regenerated goldens, dependency patches and lockfiles.
   Use a clean checkout for all release build inputs. `scripts/release-checkout.cjs` checks the actual
   commit and staged, unstaged and untracked build inputs immediately before each public deployment
   step. Deployment receipts are outputs and may be written during a deployment.
2. Run the Release workflow on the candidate before tagging. It requires Solidity tests/static
   analysis, Rust tests/lints, two independent cold Docker guest builds, and all seven native/TS/EVM/
   guest parity jobs. Guest consumers use the **same archive** agreed upon by those cold builds.
3. Every detached guest lockfile is checked before SP1's metadata discovery and the build uses
   `--locked`. The exact builder image is in `zk/sp1-builder-image.txt`. Changes to this file are
   verification-key changes until independently reproduced otherwise. The build and host reject a
   different `SP1_DOCKER_IMAGE`; local artifacts require explicit `TRUSTGRAPH_GUEST_BUILD=local` and
   cannot be used with `TRUSTGRAPHS_RELEASE_BUILD=1`.
4. The candidate proof jobs require `SP1_NETWORK_PRIVATE_KEY` and
   `EAS_OFFCHAIN_TESTNET_RPC_URL` repository secrets. They purchase real Groth16 proofs for all seven
   programs, compare embedded keys/digests with the candidate manifest, and verify each proof through
   `SP1JournalVerifier` and the actual Sepolia gateway on a read-only fork. Changed keys, journals and
   seals must fail. No public transaction is sent by this gate. Evidence artifacts retain source SHA,
   key, gateway, block, proof files and digests for 90 days.
5. Image publication depends on those proof jobs. Tagging the reviewed candidate creates the release
   using the same gates. A manual workflow run currently publishes an `edge` image; it does not create
   a release tag. Download `guest-manifest.json` from the successful candidate/release run, verify its
   workflow provenance, and set `DEPLOYMENT_COMMIT` to its exact SHA. Preflight derives the candidate
   identity from that manifest, with no hard-coded prior release.

Deployment rejects manifests with local/incorrect builder identity, malformed/duplicate program
entries, absent ELF digests, or keys/digests different from the archived candidate. Existing Sepolia
deployment records remain historical evidence; do not relabel their addresses as new v0.1.0 contracts.
These fixes change contract bytecode and multiple guest keys. Build new verifiers and factory
generations, then migrate explicitly where appropriate.

Solidity is pinned to 0.8.36 with the existing via-IR, Cancun and optimizer settings. EAS 1.9.0
otherwise requires exactly 0.8.29, so the pnpm patch changes its 15 exact compiler pragmas only.
Canonical chain EAS/Safe contracts retain their existing deployed code. Their identity must come
from the configured external deployment, not from recompiling package source locally. The compiler
upgrade addresses the subsequently fixed issues listed in the [official Solidity bug registry](https://docs.soliditylang.org/en/latest/bugs.html).

## Testnet operation before mainnet

The genuine-proof CI gate validates the verifier adapter. It does not replace testing complete
factory-to-consumer state transitions on the candidate deployment. Record the following with exact
contract addresses, transaction hashes, source SHA and guest-manifest digest:

- Each enabled factory's creation, first proof acceptance, invalid proof rejection, changed-params
  checkpoint, repeat-statement nonpayment and subsequent distinct-statement payment.
- Standard signer bootstrap, insufficient-activity preview, successful selection, votes arriving
  during proving, expiry refresh and governance recovery. Weighted/composition/hybrid signer
  selection remains unsupported and rejected.
- Funding, claim, pause/unpause and sweep with the effective claim deadline; direct and vault proof
  submissions; recovery proposer rotation and expiry; child-approved authority migration.
- Current imported-head completeness, required badge-definition availability, relayer admission
  validation and loss of an archive. Invalid or missing required witnesses now stop proving until a
  valid replacement or a publicly determined expiry; they cannot privately select a different root.
- The complete governed-instance migration described in [production operations](production.md),
  including replacement governance/signer modules and preservation of old claims.

Permissionless native attestation ingress is retained for the candidate. The existing host's 1,800
raw-record profile is a calibrated operational bound, not on-chain admission control; the 200,000
registry/payment envelope does not make arbitrary native histories provable. The scoring changes
require fresh candidate cycle measurements before raising limits or reusing old cost estimates.
Keep the 80% capacity alert, budget migration lead time, and archive all accepted inputs. Admission
economics or authenticated incremental state is still required before unbounded, adversarial native
histories can safely support significant mainnet value. A simple lifetime guest cap would strand old
instances and is deliberately not used as a liveness fix.

The mainnet deployment writer remains disabled until a separate mainnet profile and this evidence
are reviewed. Nothing in the local remediation marks public-chain tests or an independent final
audit as completed.
