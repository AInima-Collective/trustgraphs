# Trustgraphs v0.1.0: contract security and architecture review

Reviewed commit: `a45687bfdf0cc5c3190aea9048b9ec79b24c3150`, 2026-09-05. Scope: production Merkle snapshot/verifier/distributor, EAS resolvers/importer/router/accumulators, anchor registries, composition adapter/accumulator, instance/subnetwork registries, proving vault, related interfaces and validator seams. Governance modules/factory control planes were delegated elsewhere. Existing frontend changes were preserved. Production code was not changed.

This is a source review with targeted reproductions, not an independent certification of the SP1 proof system or a substitute for deployment verification. Prior findings and remediation were checked against `research/audits/2026-08-23-pre-testnet.md`, `research/plans/pre-testnet-audit-closure.md`, and `research/premainnet-audit-2026-08-13-outstanding.md`. No unconditional third-party fund theft or root-forgery bug was established in this scope.

## Findings

### CS-1 — Changed scoring parameters cannot take effect on a quiet graph

**Severity: Medium (liveness/API correctness). Confidence: High, reproduced. Recommendation: fix before mainnet; preferably before tagging because it changes checkpoint semantics.**

Locations:

- `contracts/src/merkle/MerkleSnapshot.sol:324-331`: a parameter rotation is documented to take effect at the next trigger.
- `contracts/src/merkle/MerkleSnapshot.sol:427-436`: the no-change check compares only the two lane commitments and counts; it ignores the newly configured `paramsHash`.
- `contracts/src/merkle/MerkleSnapshot.sol:449-450`: only a new trigger can pin the new parameter hash.
- `contracts/src/merkle/MerkleSnapshot.sol:491-502`: applied checkpoints are stale and existing checkpoints remain pinned to the old parameters.

Scenario: accept a score root, then legitimately rotate trusted seeds, scoring parameters, or the weighted prior while no vouches arrive. The parameter update succeeds and the configuration reads back correctly, but `trigger()` continues reverting `NoNewInputs` indefinitely. The old checkpoint cannot be proven under the new parameters, and the accepted checkpoint cannot be resubmitted. Creating an unrelated new input is currently the only way to apply the new scoring configuration. Verifier upgrades after the last checkpoint was applied have a related inability to refresh without input movement.

The existing anti-replay rationale is valid for identical statements, but a new `paramsHash` is a different proven statement. Do not remove the no-change guard wholesale: preserve duplicate-statement protection and deliberately support configuration changes. At minimum include the last checkpoint's pinned parameter hash in the equality check. Consider an explicit configuration revision for program upgrades while preserving the documented submission-time verifier emergency override. Review vault statement identity at the same time: `_terms` at `ProvingVault.sol:311` omits params/verifier identity, so allowing multiple configurations with identical inputs and output root may otherwise suppress legitimate new bounties. A larger but clearer pre-mainnet design is an explicit checkpoint/version/domain field in the shared journal, with explicit payout deduplication semantics.

Test evidence: `test_ChangedParamsCannotBeCheckpointedWithoutUnrelatedInput` in `research/audits/2026-09-05-v0.1.0-reproductions/solidity/ReleaseReadinessPoC.t.sol` uses the production `MerkleSnapshot` and production accumulator implementation. It accepts checkpoint 0, changes params, advances 10,000 blocks, verifies the trigger revert and old pinned params, then shows an unrelated edge permits checkpoint 1 under the new params. The verifier is mocked because this finding occurs in checkpoint creation, before proof verification.

Separate design point: a completely unchanged source becoming too old for `CompositionSourceAccumulator.maxAgeBlocks` is the documented freshness rule, not a second defect in this finding. Decide how operators should refresh intentionally quiet sources; don't silently equate that rule with the changed-parameters case.

### CS-2 — Contributions still admit EAS expiration metadata that the proven allocation ignores

**Severity: Low (semantic inconsistency; monetary allocation relevance). Confidence: High, reproduced at ingress and confirmed in the guest reconciliation code. Recommendation: reject expiring contribution records before shipping contributions with real funding.**

Locations:

- `contracts/src/eas/resolvers/ContributionResolver.sol:122-133`: accepts and folds contribution claims/responses/valuations without checking `attestation.expirationTime`.
- `contracts/src/eas/AttestationAccumulator.sol:108-114`: the authenticated leaf has no expiration field.
- `crates/contributions-core/src/reconcile.rs:47-55`: reconciliation excludes explicit revocation kinds only; no expiration information is available.
- `contracts/src/eas/resolvers/EASIndexerResolver.sol:83-86`: the native trust resolver already rejects nonzero expiration, providing the minimal consistent fix.

A valuation or contributor response with an EAS expiration remains part of the proven allocation after that time unless explicitly revoked. This can contradict the actor's intended consent/rating lifetime. It is not a way to forge another actor's authorization: the actor submitted the record, and the guest faithfully computes the current implemented rules. The problem is that ingress accepts a standard semantic field it cannot honor.

The August audit's L-3 closure was scoped to `EASIndexerResolver`; the sibling contribution resolver still has the same omission. The cheapest remedy is the same `ExpirationNotSupported` guard for all three contribution schemas, with tests for claim/response/valuation. Supporting actual expiration would require authenticating its value and the evaluation time or an explicit authenticated expiration operation; that is a larger program/journal decision.

Test evidence: `research/audits/2026-09-05-v0.1.0-reproductions/solidity/ContributionExpiryPoC.t.sol` deploys actual EAS and SchemaRegistry contracts, submits an expiring valuation to the actual ContributionResolver, and verifies it remains the same permanent fold after expiry. This proves the ingress/commitment behavior, not an end-to-end monetary payout. Guest source inspection establishes why no expiration filtering is possible from that fold.

### CS-3 — The subnetwork depth invariant can be bypassed by attaching ancestors after descendants

**Severity: Low (metadata/integration correctness). Confidence: High, reproduced through the public consent handshake. Recommendation: fix or accurately redefine the invariant before integrations depend on it.**

Locations:

- `contracts/src/registry/SubnetworkRegistry.sol:18-19`: promises each child has at most 16 accepted ancestors.
- `contracts/src/registry/SubnetworkRegistry.sol:43`, `:62`, and `:141-148`: validation walks only the new parent's ancestors, ignoring existing descendants of the child being attached.

Create A → B, then B → C, then C → D, and continue. Every newly selected parent is a root, so every local check sees a depth of one. The earliest child acquires arbitrarily many ancestors. The reproduction builds 33 ancestors using `claimParent` and `acceptChild`, without REGISTRAR_ROLE. This does not confer Safe power: the contract explicitly defines these links as metadata. It can invalidate consumers that allocate a maximum of 16 traversal steps or rely on the documented invariant.

Choose a clear model: disallow reparenting nodes that already have descendants, maintain bounded subtree height and update ancestors on changes, or state that 16 is only the insertion-time traversal bound and make all consumers tolerate deeper existing trees. If the current global bound remains the API promise, add a stateful invariant test over arbitrary claim/accept/release order; current tests primarily exercise one construction direction.

Test evidence: `test_BuildingHierarchyFromLeavesExceedsDeclaredMaximumDepth` in `research/audits/2026-09-05-v0.1.0-reproductions/solidity/ReleaseReadinessPoC.t.sol`.

## Material existing design constraints to retain in the release decision

These are not refiled as newly discovered exploits.

1. **Permanent input growth is still the main native-lane availability risk.** `EASIndexerResolver.onAttest` and `ContributionResolver.onAttest` are open to schema users and ultimately call `_foldAt` with no capacity/admission mechanism. The full history is cumulative, and `MerkleSnapshot.setAccumulator` rejects rotation after checkpoint history exists (`:315-318`). The current operator's default raw-record envelope is 1,800 (`crates/operator-core/src/work.rs:14`), distinct from the 200,000 protocol constant. Relayer controls on offchain anchors do not protect the native lane. A mainnet recovery design needs concrete instance migration and consumer/governance continuity; monitoring alone reports the cliff. This issue was acknowledged in earlier audits and should remain explicit rather than be called solved by configurable operator limits.
2. **Imported schema coverage is an external trust/availability rule.** `OnchainAttestationImporter.sol:23-25` accurately says it authenticates included records, not completeness of the source schema. Any caller can import attestations and checkpoint before someone imports known revocations/expirations. The atomic creation router closes new-attestation ingress for its own call but not all EAS source activity. Public claims and integrations must distinguish native inline completeness from completeness of the processed subset. Decide which authoritative backfill/sweep/finality policy gates first funding and governance use.
3. **Distributor pause still consumes the claim window.** `claim` is paused (`MerkleFundDistributor.sol:377-381`), claim deadlines remain absolute (`:398-402`), and expired sweeps are available while paused (`:458-505`). The previous M-8 fix restores the funder's exit; it does not preserve contributors' usable claim time. The owner can intentionally or accidentally pause through expiry, after which the funder receives the unclaimed budget. Either explicitly accept that Safe's authority over claim availability or add paused-time accounting/extension semantics. Do not say the prior fix protected both sides of this tradeoff.
4. **Composition deliberately fails closed on source changes and staleness.** Adapter registry/verifier/codehash identity pins and source max-age bounds are strong protections, but a source migration/registry correction can stop every dependent composition until its policy changes. Exercise this operational path before mainnet; preserve the distinction between approved migration and a permissionless bypass.
5. **Vault fallback claiming depends on provenance recording.** `ProvingVault.claim` calls `getAcceptedCheckpoint` (`:283`), while snapshot accepted-history storage is conditional on `provenanceEnabled` (`MerkleSnapshot.sol:544-559`). Supported factories enable it at creation; low-level snapshots default to false and cannot enable after first state. Consider enforcing the prerequisite when binding a funded vault account, or documenting it in the low-level API. Otherwise unsupported manual deployments can lose the advertised front-run-resistant fallback claim path.

## Architecture and code-quality recommendations

- Keep the shared journal binding and deterministic leaf codecs as the small security core. Explicitly version checkpoints/configuration/payout identity, and document which identity each layer uses. Current deduplication is distributed across trigger lane equality, monotonic checkpoint IDs, recipient storage, accepted-history optionality, and a separate partial statement key in the vault; this coupling produced CS-1 and is hard to change safely after deployment.
- Validate irreversible deployment inputs uniformly: `SP1JournalVerifier` still accepts zero/invalid gateway and zero vkey at construction; `TrustAccumulatorMirror.bindSnapshot` lacks the reciprocal accumulator check its siblings use. Existing calls fail closed and supported deployers wire these atomically, so this is deployment-quality hardening, not a root-forgery finding.
- Treat snapshot hooks as an explicit failure boundary. State writes currently invoke hooks before all optional provenance has been stored (`_updateStateAtBlock` called at `:543`, provenance written at `:544-559`, hooks at `:652-657`). Consider completing the full accepted-state record before callbacks and adding reentrancy protection so future consumers cannot observe partially finalized provenance. The shipped MerkleGovModule does not establish a concrete exploit here; this is future-proofing the extensible API.
- Specify supported token behavior for the generic distributor. Balance-delta funding and per-round spending limits are good defenses, but they do not make arbitrary rebasing or sender-tax tokens share-safe: recorded budgets can diverge from later actual balances/debits. Either scope support to ordinary transfer behavior or test/document the exact supported fee-on-transfer model. Similarly, snapshot fee terms before token callbacks rather than rereading mutable fee globals after `safeTransferFrom`.
- Simplify comments after the release: many production NatSpec blocks carry historical exploit narratives, resolved alternatives, and stale statements (e.g. `ContributionResolver.sol:23-24` still says the native resolver tolerates garbage schemas, and `TrustAccumulatorMirror.sol:16` describes an accumulator-local no-change guard that is now in snapshot). Move historical rationale to linked design/ADR documents; leave current authority, invariants, and API semantics in code. This materially reduces review friction without removing the valuable history.
- Add focused stateful tests for configuration changes with quiet inputs; public subnetwork mutation order; all contribution schema expiration variants; provenance/vault binding prerequisites; and root acceptance followed by standalone claim after oracle/funding recovery. Preserve negative tests against duplicate statements while adding config-change support.

## Positive findings

- Snapshot journals bind both input lanes, pinned parameters, output root, blob digest, CID-string digest, total value, skip commitment, payee, and a chain/snapshot-derived domain. Historical writes use the input-freeze block and reject checkpoint rollback.
- Accumulators are snapshot-bound; native EAS schema ingress fails closed before binding and rejects foreign schemas. Strict EAS offchain ingress authenticates owner-signed append transitions and bounds retained-entry work.
- Distributor funding pins root, denominator, expected fee recipient, and maximum fee. Each claim is account-bound and limited by its round's remaining budget; funding measures received token balance.
- Vault accounts bind to a snapshot once; registry updates alone cannot redirect a funded account. Constitutionally authorized migration is explicit. Fee/gas credits use pull payments, and transient price/funding failure does not automatically consume the bounty slot.
- Composition captures authenticate registry identity, snapshot/verifier codehash and program key, source root/provenance, and source age. Prior foreign-registry admission and wrong-checkpoint vault-claim findings are fixed in current code.
