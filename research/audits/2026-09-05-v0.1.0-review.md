# Trustgraphs v0.1.0 readiness review

Follow-up: [implementation and validation of the fixes](2026-09-05-v0.1.0-remediation.md).

Reviewed on **2026-09-05**, against **`a45687bfdf0cc5c3190aea9048b9ec79b24c3150`**, before the proposed v0.1.0 tag. Three parallel reviewers examined contract security, zk programs, and governance/factory architecture; the coordinating review checked findings, release tooling, dependencies, and validation. Existing frontend edits were preserved. This review changes documentation and adds isolated reproductions; it does not remediate production code.

**Recommendation: hold mainnet, and fix the shared scoring and governed-instance issues before freezing the v0.1.0 contracts and verification keys.** Disposable testnet deployments remain useful for validating the fixes. Passing existing tests is insufficient: the new reproductions demonstrate incorrect behavior that the current suite accepts.

The architecture has substantial strengths: small guest entrypoints, canonical Rust cores, deterministic encodings, explicit proof journals, isolated guest dependency graphs, typed parameter controllers, atomic Safe installation, and considerable regression coverage. The most consequential remaining problems occur between these components: what constitutes an eligible edge, when a no-op becomes initialization, which guest supports which factory, and which changes permit a new checkpoint. These deserve priority over general refactoring.

No unconditional third-party theft or cryptographic proof forgery was established in the standard trustgraph path. This is a source review with native and EVM reproductions, **not a formal audit, a review of SP1 internals, or certification of deployed addresses**. No fresh SP1 execution or genuine Groth16 proof was produced here. Imported-program findings describe what the guest relation permits; they do not break the underlying proof system.

**Scope and release assumptions.** The reviewed surface includes 80 production Solidity files and 72 source files in the critical Rust core crates, plus guest wrappers and security-relevant host/build/deployment seams. Review depth was concentrated on the findings and boundaries described below; these counts are not line-coverage claims. Frontend and indexer implementation were outside scope. The checked-in Sepolia profile supports standard, weighted, composition, contributions, governance and signer components. Hypercerts and Nostr were reviewed because they also freeze durable statements and may be enabled later. Mainnet is deliberately disabled in the deployment tooling; that is an appropriate safeguard until a reviewed profile exists.

The tracked [Sepolia manifest](../../deployments/sepolia.json) is historical deployment evidence: it identifies an older source revision and SP1 6.3.1 guests. Current guest manifests pin SP1 6.6.0. The historical addresses and keys must not be relabeled as this reviewed release.

**Prioritized findings.** “Before freeze” means before publishing the intended durable v0.1.0 contract/guest artifact set. Conditional findings block the affected feature, not every program. The detailed supporting reviews contain full traces and test explanations.

**R1 — Make positive-weight reachability a single invariant.**

The BFS traverses all keys, including zero-weight edges, at [pagerank.rs:104](../../crates/pagerank-core/src/pagerank.rs#L104), while transitions exclude zero weights at line 220. That contradicts the [positive-weight reachability specification](../../docs/concepts/algorithm.md#L34). A native pipeline reproduction with admissible computational parameters changes a disconnected two-account ring from zero standing to **71.9% of the pool** by adding a zero-weight edge from the seed when the starting share is 50%. With the default 100% starting share, a zero-weight shortcut boosts a downstream score by about **52%** by shortening its decay distance.

This requires a real zero-weight vouch from a reachable account; it does not let an attacker forge the seed's signature. It affects standard trustgraphs, signer scoring, and other users of the shared ranker. Weighted-prior uses a separate recurrence. Use the same positive/non-self predicate in BFS and transitions. Add semantic properties that zero edges cannot affect scores or distance, including both settings above. Equality with an older implementation is insufficient if both retain the same mistake. Rebuild every affected guest and its vectors. See [ZK-01](2026-09-05-v0.1.0-zk.md#zk-01--zero-weight-vouches-grant-reachability-and-shorten-trust-decay).

**R2 — Separate successful signer selection from checkpoint consumption.**

[SignerSyncZkModule.sol:293](../../contracts/src/zodiac/SignerSyncZkModule.sol#L293) sets `hasAppliedCheckpoint=true` even when the guest returns the unchanged singleton owner set because it lacks enough activity. The next proof uses that flag as `was_initialized`. [The core](../../crates/pagerank-core/src/signer.rs#L129) then requires two active **current owners**, impossible while there is only one. The operator skips these no-op results, but anyone can prove and submit them directly. Member governance and recovery remain available; the failure is automatic signer initialization, not a total Safe lock.

Commit an explicit selection outcome or make insufficient-activity results unprovable, and keep initialization distinct from the replay high-water mark. Test the actual factory bootstrap through native guest logic and contract acceptance, including an adversarial no-op followed by sufficient activity. The native reproduction uses factory-admissible seeded parameters; a separate mock-verifier EVM test demonstrates the contract transition. See [G-01](2026-09-05-v0.1.0-governance.md#g-01--a-valid-no-op-signer-proof-permanently-exits-singleton-bootstrap).

**R3 — Authenticate the configured Safe implementation, not a recompilation of another version.**

[GovernedFactoryBase.sol:210](../../contracts/src/factory/GovernedFactoryBase.sol#L210) derives proxy addresses from the configured factory but pins runtime identity using local `type(SafeProxy).runtimeCode`. The configured canonical Sepolia factory creates a 171-byte proxy; the local artifact is 114 bytes. Their hashes differ. A fork reproduction first creates an ordinary canonical Safe successfully, then predeploys all 16 deterministic bootstrap candidates and confirms `BootstrapSafeUnavailable`: the wrapper rejects otherwise adoptable canonical proxies.

Pin the actual audited factory/singleton/proxy artifact set and retain the full bootstrap state checks. Include both unsquatted creation and predeployment adoption on a fork of the exact release dependencies. This revives a creation-griefing condition despite the earlier local-factory fix; it does not steal the Safe. The canonical address is corroborated by the [official Safe deployment registry](https://raw.githubusercontent.com/safe-global/safe-deployments/main/src/assets/v1.3.0/proxy_factory.json); bytecode mismatch and denial of service were measured separately. See [G-02](2026-09-05-v0.1.0-governance.md#g-02--canonical-safe-proxies-fail-the-bootstrap-adoption-codehash-test).

**R4 — Enforce program compatibility at factory entrypoints.**

The [weighted](../../contracts/src/factory/GovernedWeightedTrustgraphsFactory.sol#L81) and [composition](../../contracts/src/factory/GovernedTrustComposeFactory.sol) wrappers accept enabled signer sync. The installed signer guest only computes the standard PageRank parameter commitment. The snapshot expects weighted or composition commitments with different encodings, so genuine proofs cannot satisfy the contract journal. Current mock-verifier plumbing tests conceal this mismatch.

Reject these combinations now, following the existing [hybrid rejection](../../contracts/src/factory/GovernedTrustgraphsFactory.sol#L113). If support is required, design a statement that authenticates the appropriate accepted score distribution and its completeness, or provide dedicated signer programs. Publish and enforce a matrix of program ID, parameter encoding, output type, and compatible consumers. See [G-03](2026-09-05-v0.1.0-governance.md#g-03--weighted-and-composition-factories-can-enable-a-signer-guest-that-cannot-prove-their-parameters).

**R5 — Define checkpoint and payout identity together.**

[MerkleSnapshot.trigger](../../contracts/src/merkle/MerkleSnapshot.sol#L427) compares only the two lane commitments with the preceding checkpoint. Changing seeds, parameters, or a weighted prior on a quiet graph cannot create a checkpoint under the new configuration. The reproduction accepts a root, updates parameters, advances 10,000 blocks, and still gets `NoNewInputs`; unrelated ingress is required to proceed.

At minimum include the last pinned parameter hash in the equality check. Define the policy for program-version changes as well. Preserve duplicate-work prevention: do not simply remove the guard. Review [vault statement deduplication](../../contracts/src/vault/ProvingVault.sol#L311) in the same change because its key omits parameters/verifier identity; distinct recomputations with equal inputs and outputs may otherwise receive only one bounty. An explicit versioned statement/checkpoint identity would make these rules easier to audit. Source-age expiry in composition is a separate intentional freshness rule, not a duplicate finding. See [CS-1](2026-09-05-v0.1.0-contracts.md#cs-1--changed-scoring-parameters-cannot-take-effect-on-a-quiet-graph).

**R6 — Replace or constrain the legacy remainder policy.**

[distribute.rs:27](../../crates/pagerank-core/src/distribute.rs#L27) truncates scores to a `1e6` quantum, sorts descending, and gives all residual points to the final account. With an admitted pool of one, the complete native pipeline assigns the whole pool to the lower-ranked recipient and removes the higher-ranked seed from the output. With pool two, an account with a score of just `1/1e18` can receive half the pool after its quantized score becomes zero.

This is documented legacy behavior, but it is a poor default API guarantee where output points determine governance and signer eligibility. The integer-remainder effect is tiny with the usual large pool; the quantization precision floor is separate. Prefer full-precision deterministic largest-remainder apportionment, reusing the approach already present in [weighted prior](../../crates/weighted-prior-core/src/rank.rs#L30) and [composition](../../crates/composition-core/src/hamilton.rs). Define quota, ordering, exact-total, zero-value and small-pool properties. See [ZK-04](2026-09-05-v0.1.0-zk.md#zk-04--legacy-remainder-allocation-can-invert-ranking-or-reward-a-zero-quantized-account).

**R7 and R8 — Keep imported-program authority conditional on stronger statements.**

Nostr [filters configured seeds to the current graph](../../crates/nostr-workspace-core/src/compute.rs#L329). If none remain, the ranker receives an empty seed set and enables unseeded scoring. A signed-fixture reproduction with a valid but currently absent seed pays the full `1e24` pool to three non-seed nodes, exactly as an explicitly unseeded run. Preserve configured seeds or fail with a defined outcome; absence must not erase the trust boundary.

Separately, both Nostr and Hypercerts allow the prover to omit required witnesses and obtain fallback/drop outputs. With the same Nostr anchors, parameters and instance binding, omitting one available roster witness changes a nonzero root to zero and still returns a valid computation. A committed `skippedDigest` records a choice; it does not establish that data was unavailable to other provers. Permissionless acceptance makes the first such proof authoritative for that checkpoint. This is existing imported-program discretion, partly acknowledged for Hypercerts in earlier reviews, not a failure of native strict EAS completeness.

Before these roots control value, either require every committed required payload, commit an independently authenticated selection/availability decision, or enforce an explicit trusted acceptance/challenge boundary. Role-gated anchor admission alone does not constrain the later prover's omissions. Do not weaken strict EAS fail-closed behavior to copy this design. See [ZK-02 and ZK-03](2026-09-05-v0.1.0-zk.md).

**R9 and R10 — Close the remaining contract API inconsistencies.**

[ContributionResolver](../../contracts/src/eas/resolvers/ContributionResolver.sol#L122) accepts expiring claims, responses and valuations, but the authenticated leaf and contribution reconciliation carry no expiration information. An actual EAS reproduction confirms an expiring valuation enters the permanent fold. Reject nonzero expiration as the native trust resolver already does, or explicitly authenticate expiration semantics in a new program. The demonstrated test covers ingress/commitment, not a full monetary payout. See [CS-2](2026-09-05-v0.1.0-contracts.md#cs-2--contributions-still-admit-eas-expiration-metadata-that-the-proven-allocation-ignores).

[SubnetworkRegistry](../../contracts/src/registry/SubnetworkRegistry.sol#L141) checks only the new parent's ancestors. Constructing descendants first, then adding ancestors, produces 33 ancestors using the ordinary two-party consent flow despite `MAXIMUM_DEPTH=16`. These links are metadata and confer no Safe power. Maintain a real subtree bound, restrict attachment, or accurately redefine the API guarantee; test mutation order as a stateful invariant. See [CS-3](2026-09-05-v0.1.0-contracts.md#cs-3--the-subnetwork-depth-invariant-can-be-bypassed-by-attaching-ancestors-after-descendants).

**R11 — Make release provenance describe the code actually compiled.**

[requireReleaseCommit](../../contracts/deploy/env.ts#L94) validates only the shape of the supplied commit. Manifest verification compares that supplied value to another supplied file; [deployment validation](../../contracts/deploy/env.ts#L1159) never checks checkout identity or relevant working-tree changes. [The deployer](../../contracts/deploy/deploy-contracts.ts#L200) then invokes Forge on the current checkout and [writes the supplied commit](../../contracts/deploy/env.ts#L1862) into deployment history. An operator can inadvertently deploy modified Solidity while the record claims a reviewed release. Existing planning tests even pass using `aa...aa` as the declared commit in the current checkout.

The [preflight](../../scripts/sepolia-preflight.sh#L22) still pins `v0.0.5` and `f64a4c7...`; it prints HEAD and dirty-path count instead of requiring a match. Use a fresh immutable checkout or a verified artifact bundle for deployment. Check source identity and relevant untracked/modified files, record constructor inputs and runtime hashes per deployed generation, and retain historical entries rather than rewriting all contracts under one release label. Derive the release reference from one candidate manifest instead of another hardcoded shell constant. Treat the older Sepolia history as history, not as evidence for new guests.

**R12 — Use one guest artifact set from testing through release.**

The reproducibility workflow and image/table comparison are good controls. However, the [real-testnet Groth16 job](../../.github/workflows/eas-offchain-assurance.yml#L231) builds guests using plain `cargo prove build`, while the release uses the Docker builder. The host can then [fall back to local ELFs](../../zk/prover/build.rs#L135). This can test a different vkey or fail against the deployed one. Four guest workspaces also build without `--locked` in [both build entrypoints](../../scripts/build-guests.sh#L30); two cold builds agreeing at one moment do not prove that the committed lockfiles remained authoritative.

Consume the candidate's exact archived ELFs/image for real-proof tests, require all guest lockfiles, pin/record the builder image digest, and disable local fallback in release mode. Verify the candidate source, guest digest, vkey, contract artifact, and real proof together. Keep a developer-only local build mode.

The [release workflow](../../.github/workflows/release.yml#L22) requires guest reproducibility and image verification, but does not itself require the Solidity, Rust, program parity, or real-proof gates. Those are separate PR/scheduled workflows. External branch/tag protections might compensate, but were not inspected here. Make the release promotion job depend on evidence for the exact candidate SHA, including every enabled program/consumer combination. Do not silently reuse a weekly proof from another revision.

**Architecture decisions required before mainnet.** These are separate from newly reproduced implementation defects.

| Decision | Evidence and consequence | Recommendation |
| --- | --- | --- |
| Native input admission and lifetime growth | Native `_foldAt` is append-only and has no ingress capacity enforcement. The operator default is 1,800 raw records; the 200,000 protocol constant is not its measured capacity. Once checkpoints exist, accumulator rotation is locked. | Resolve the previously acknowledged bloat risk with admission/economic limits and/or an incremental/windowed statement. Exercise a full migration preserving authority, claims, consumers and vault funds. Monitoring detects exhaustion; it does not restore capacity. |
| Signer activity liveness | Every direct vote changes the live head required at submission, invalidating prepared proofs. A member can repeatedly use `proposeWithVote`; the guest also replays lifetime activity outside its inactivity window. | Define stable activity epochs or authenticated bounded latest-activity state, a finite acceptance interval, and a separate work budget. Preserve completeness. See G-04. |
| Platform registry authority over child funds | The registry operator can change a parent's `paramsAuthority`; Admin-tier `ParentAuthorityModule` dynamically resolves it into child Safe execution authority. | Treat the platform operator as a transitive treasury administrator if retained. Prefer dedicated, child-consented authority bindings and explicit migration approval. This is a high-impact trust assumption, not an outsider exploit. See G-05. |
| Strict offchain availability and recovery | An admitted malformed prefix or permanently unavailable payload prevents all later strict proofs; the registry validates owner authorization, not full payload consistency. Per-owner history also has a lifetime 2,048-entry limit. | Treat relayers as admission validators with durable archives. Test poisoned-prefix and archive-loss migration, including revocations at capacity. Do not solve liveness by permitting arbitrary skips. |
| Import completeness | Existing-schema import authenticates the included subset, not every source-schema event; external revocations/expirations may be omitted until swept. | State this distinction in program guarantees and require a tested import/backfill/finality policy before authority or funding uses imported roots. |
| Recovery and distributor timing | Old queued recovery actions survive proposer changes; pausing claims can consume an absolute claim deadline, after which funds can be swept. | Specify whether these powers are intended. Add expiry/generation cancellation and paused-time treatment where required; do not imply rotation/pause automatically protects all parties. |

**API and code-quality recommendations.**

- **Keep immutable cores small, but make migration a supported operation.** A registry update alone does not migrate immutable controllers, signer snapshot bindings, hooks, pending proofs, old distribution claims or vault accounts. Provide a tested transaction sequence for each program, including governance and recovery execution through the actual Safe.
- **Choose one typed source of truth for each compatibility and validation rule.** Share edge eligibility; enforce selection bounds on every setter, not just deployers; expose enough parameter preimages for independent operators; validate required provenance support when binding a funded snapshot. Keep program-specific semantics explicit rather than unifying unlike programs behind a hash-only interface.
- **Prefer structures over parallel argument arrays.** A proposal-action tuple and explicit checkpoint/statement structures make invariants easier to maintain. Keep telemetry outside consensus outputs, and make core APIs consistently return typed validation errors at input boundaries. Panics inside a guest remain fail-closed, but are a poor reusable host API.
- **Test semantics across component boundaries.** Preserve golden vectors and owner-diff fuzzing, then add independent zero-edge/allocation properties, factory-to-guest compatibility fixtures, exact external Safe artifacts, and stateful sequences of parameter changes, activity, linking, migration and claims. Mock-verifier tests prove plumbing; they cannot prove that an accepted journal is producible by the pinned guest.
- **Refresh the compiler and document applicability of known bugs.** The repository pins solc 0.8.29 with via-IR/Cancun. The official list includes four subsequently fixed issues covering that version, including conditional transient-clearing and recursive-spill bugs. This review did not establish an exploitable trigger in Trustgraphs; a version match alone is not such evidence. Evaluate a pinned release containing those fixes (0.8.36 or later), then rerun bytecode-size, canonical-dependency and behavior checks. See the [official compiler bug list](https://docs.soliditylang.org/en/latest/bugs.html). Compiler changes also reinforce why external proxy identity must not come from a local recompilation.
- **Retain the helper deployers and strong existing controls.** Fresh-build measurements keep all production runtime bytecodes below 24,576 bytes: the largest is `TrustComposeParamsControllerDeployer` at 21,613 bytes, followed by `TrustgraphsFactory` at 21,207 bytes. Keep code-size checks in CI. Preserve journal binding to both lanes, parameters, output/CID, payee and instance/chain; snapshot monotonicity; Safe role handoff; funder-pinned distribution terms; per-round spending bounds; pull-payment credits; and composition provenance checks. Broad rewrites would add risk without addressing the concrete findings.
- **Move obsolete history out of production NatSpec.** Correct stale field counts and old lane/role descriptions; keep current invariants and authority beside code, and link historical audit rationale. Align package/release version policy (`0.4.0` npm root, `0.9.3` Rust workspace, `0.1.0` guests) explicitly so artifact consumers do not infer an unintended correspondence.

**Recommended implementation sequence.**

1. Freeze an explicit v0.1.0 feature matrix. Disable unsupported weighted/composition signer combinations immediately; keep Nostr/Hypercerts authority conditional on R7/R8. Reassess whether signer rotation needs to ship at all for the initial owner-locked governance Safe.
2. Fix R1–R6 and R9/R10 as applicable, together with the checkpoint/payout identity decision. Address signer activity liveness if signer sync remains enabled. Add the cross-component regressions before regenerating artifacts.
3. Build all affected guests once from frozen dependencies in the pinned builder, regenerate vectors and vkeys, and publish a manifest linking exact source, compiler settings, program identities and contract artifacts. Resolve R11/R12 rather than deriving production pins from a developer cache.
4. Rehearse each enabled factory and consumer on Sepolia using those exact artifacts: genuine proof acceptance and invalid-proof rejection, governance and recovery, rotation/migration, funding/claim fallback, supported external dependency versions, and hostile input/activity patterns at measured capacity.
5. Before first mainnet value, resolve the authority/admission/availability decisions above, implement and review a mainnet profile, obtain an independent review of the final remediation diff and frozen guest statements, and retain the testnet evidence with the release. Successful testnet operation alone does not close an adversarial design finding.
