# Trustgraphs v0.1.0 ZK and canonical Rust review

Reviewed commit: `a45687bfdf0cc5c3190aea9048b9ec79b24c3150`. Review date: 2026-09-05. Production sources were not modified. This report reviews source statements and native behavior; no fresh SP1 ELF build, execution, Groth16 proof, or on-chain proof acceptance was performed in this environment.

## Recommendation

Fix the positive-weight reachability inconsistency before freezing v0.1.0 verification keys. Decide and test the integer allocation policy before attaching governance or signer selection to small pools. Keep imported Hypercerts/Nostr programs out of value-bearing permissionless use until the prover's witness-omission discretion is either removed or made an explicit, enforced trust boundary. Nostr also requires the missing-seed fix.

## Confirmed findings

### ZK-01 — Zero-weight vouches grant reachability and shorten trust decay

**Severity: Medium; confidence: high; applies to the standard launch path.** This is a scoring-semantics/influence-boundary defect, not forged signature acceptance. An attacker cannot manufacture another account's vouch; the trigger is an existing or deliberately submitted zero-confidence vouch from a reachable account.

`crates/pagerank-core/src/pagerank.rs:104` traverses every map key in the BFS, including weight zero. The transition kernel at lines 220–235 explicitly excludes zero weights. Consequently the definition of reachability/distance disagrees with the definition of an influence-carrying edge. `docs/concepts/algorithm.md:36` explicitly promises positive-weight reachability.

Two reproduced effects:

- With one seed, two otherwise disconnected mutually vouching accounts, and `trust_share_fp = 0.5*S`, adding only a weight-zero seed-to-ring edge changes the ring's allocation from zero to approximately **71.9% of the pool**. Full native pipeline output: seed `281024281024281025`, ring accounts `344323344323344323` and `374652374652374652`, from pool `1e18`.
- With the default `trust_share_fp = S`, a zero-weight shortcut across a positive chain changes the distance decay without taking any outgoing budget. The reproduced downstream score rises from `47526169140983277` to `72326111344680626`, about **52%**.

The full-pipeline reproduction uses native schema field 1, min weight zero, max weight `100*S`, scale `1e18`, damping 0.85, decay 0.8, 100 iterations, tolerance `1e6`, a nonzero seed, and positive pool: values admitted by `contracts/src/params/TrustgraphsParamsValidator.sol:85` (the fixture supplies representative already-derived identity fields). These are not intentionally invalid parameters.

**Affected:** `trustgraph-core`/`trust-graph` and `pagerank-core`/`signer-sync`; contributions reputation and Hypercerts/Nostr rank also share this function. Weighted-prior uses a separate recurrence and excludes zero/self rows.

**Remedy:** share an explicit eligible-edge predicate between BFS and transitions; traverse only positive, non-self weights. Add metamorphic properties that adding/removing a zero edge cannot alter any score, reachability, or distance, including a disconnected ring and a shortcut under full starting share. Keep an independent normative specification rather than relying only on differential equality with the old pull kernel, which can preserve the same semantics defect. Rebuild affected guests and regenerate goldens/vkeys as a coordinated release change.

**Evidence:** `research/audits/2026-09-05-v0.1.0-reproductions/rust/tests/rank.rs`, tests `zero_weight_edge_grants_teleport`, `zero_weight_shortcut_boosts_default_trust_share`, `factory_admissible_zero_vouch_full_pipeline`; all pass by demonstrating current behavior.

### ZK-02 — A missing configured Nostr seed silently activates unseeded PageRank

**Severity: High for value-bearing Nostr deployments; confidence: high.** This is scoped to Nostr, not the standard trustgraph root producer.

`crates/nostr-workspace-core/src/compute.rs:329–335` intersects the governance-pinned seed list with `graph.nodes`. The graph node universe comes from the relay roster plus eligible delegated agents (`crates/nostr-workspace-core/src/semantics.rs:497`, tail of `derive`). If no configured seed remains in that roster, the resulting set is empty. `crates/pagerank-core/src/pagerank.rs:48` defines empty seeds as unseeded/uniform PageRank. The guest therefore awards standing to remaining roster members with no trusted path from any configured seed.

The reproduction replaces the seed in the signed epoch-one fixture with the actual, valid public key of a member introduced by the epoch-two fixture; it is absent from the earlier roster. The configured-seed result pays the entire `1e24` pool to three untrusted nodes and is **byte-for-byte equal in scores to explicitly emptying the seed list**. Params validation succeeds. This can occur during membership changes; a relay roster authority effectively acquires power to disable a separately configured trust boundary without changing its params hash.

The shared ranker already unions configured seeds into its consensus universe (`pagerank.rs:158–165`), and Hypercerts now retains configured seed DIDs even with missing repo data. Nostr's prior filtering bypasses that defense.

**Remedy:** preserve configured seeds when calling the ranker, or explicitly reject/produce a defined non-authoritative empty state when required seeds are outside the roster. Decide whether an absent seed may itself receive a score; do not turn absence into an unseeded network. Test zero present seeds, partially present seeds, roster removal/re-addition, and withheld roster witnesses. Nostr guest/vkey and corresponding vectors must change.

**Evidence:** `research/audits/2026-09-05-v0.1.0-reproductions/rust/tests/nostr.rs`, `absent_configured_seed_disables_trust_gate` passes.

### ZK-03 — Imported programs let the prover choose witness availability and thus the scored root

**Severity: High for permissionless value-bearing imported programs; confidence: high.** This is an explicit implementation/design choice, partly documented in previous reviews, and should be treated as an unresolved release condition rather than presented as a new native-trustgraph vulnerability.

Nostr `compute.rs:217–220` treats an omitted witness as unavailable and proceeds to `DROPPED` at lines 255–259. Hypercerts `compute.rs:210–238` similarly allows omission/invalid witnesses to select fallback/drop outcomes. These are private witness choices, not evidence that bytes are unavailable to everyone. Committing a `skippedDigest` only records the prover's choice; it does not prove that a different choice was unavailable.

A concrete Nostr reproduction uses the exact same two anchored A+C bundles, params, and binding. Honest compute produces root `0x5fbf542ae863a5ff3c1d6a3184a5623c87e2bf34e2c39ad949a76c5676357a21`. Removing only the A witness, while retaining both anchors, produces root zero and still returns `Ok`. Both `anchor_acc` and `params_hash` remain identical. The A omission removes the roster, so every remaining event loses eligibility. This is not an unauthenticated CAR/TGNW mutation: valid published bytes already exist, and the prover simply does not supply them.

`contracts/src/merkle/MerkleSnapshot.sol:508–524` intentionally accepts the proved `skippedDigest` as output, with no required canonical selection commitment, and this acceptance path does not reject an empty root. Once an imported proof is accepted, the normal checkpoint monotonicity prevents another prover correcting that same checkpoint. The reproduction demonstrates canonical core behavior; an SP1 proof transaction was not generated in this environment.

Hypercerts already has `crates/hypercerts-core/tests/compute_fixture.rs::withheld_witness_drops_node_and_root_still_lands`, which demonstrates seed-only results after all repo witnesses are withheld. The earlier audit explicitly deferred suppression/DA risk for Hypercerts-with-value. Nostr's analogous risk should be covered by the release scope, not assumed resolved by bounded decoding, signature checks, or ingress relayer roles. A role protecting anchor admission does not restrict a later proof submitter's private witness.

**Remedy:** prefer a statement that requires every committed required payload and aborts on missing bytes, as strict EAS envelope 0 already does. Alternatively, authenticate an availability/selection manifest before proving, enforce an explicit availability committee/prover trust boundary, or provide a challenge and replacement mechanism before results gain authority. Merely publishing skip proofs cannot establish global unavailability. Test that a malicious prover cannot vary selected inputs for a fixed authoritative checkpoint, and separately test liveness under actual archive loss.

**Evidence:** `research/audits/2026-09-05-v0.1.0-reproductions/rust/tests/nostr.rs`, `nostr_omitted_valid_witness_changes_root_under_same_checkpoint` passes; existing Hypercerts withholding regression corroborates the other program.

### ZK-04 — Legacy remainder allocation can invert ranking or reward a zero-quantized account

**Severity: Medium for small integer pools; Low under the default large pool; confidence: high.** This behavior is documented as the existing last-account policy, so the recommendation is a pre-release economic/API policy improvement rather than a hidden violation of the current algorithm implementation.

`crates/pagerank-core/src/distribute.rs:27–45` quantizes scores to one million units, sorts descending, retains entries whose quantized score is zero, and awards all remaining pool to the last entry. In a small pool, rounding remainder is most of the pool, and that last entry is the lowest ranked account.

Two native reproductions:

- `total_pool = 1`, a single seed and its positive-weight recipient: the full pipeline gives the **entire pool to the lower-ranked recipient**, excludes the seed from the score set, and consequently changes which accounts can qualify for governance/signer selection. A pool of one is admitted by `TrustgraphsParamsValidator.sol:99`.
- Scores approximately `[0.5*S, 0.5*S - 1, 1]`, pool two: the dust account quantizes to zero yet receives one unit, half the pool, while the second high-ranked account receives zero.

For `total_pool=1e24` and bounded account counts, raw integer remainder distortion is tiny; do not generalize the small-pool example into a default-configuration fund-loss claim. The fixed `1e6` quantization also imposes a separate precision floor irrespective of the much larger pool.

**Remedy:** use deterministic largest-remainder apportionment with explicit tie ordering, ideally directly from full precision scores; reuse/generalize the already clear composition/weighted-prior Hamilton implementations. At a minimum drop zero quantized values and constrain/document a minimum meaningful output pool. Define properties for ordering, zero-weight exclusion, quota error, exact mass, and signer-selection stability at small pools. This affects all users of `distribute_points_generic` and requires coordinated vector/vkey changes.

**Evidence:** `research/audits/2026-09-05-v0.1.0-reproductions/rust/tests/rank.rs`, `factory_admissible_small_pool_awards_everything_to_lower_ranked_account`, `remainder_awarded_to_zero_quantum_score`; both pass.

## Bounded follow-up items, not counted as independently reproduced vulnerabilities

1. **ATProto CID policy:** `crates/envelopes/src/atproto/carset.rs:112–118` checks content hashes only for SHA2-256 and otherwise retains unchecked bytes; codec is discarded. Every followed commit/MST CID should use an enforced supported hash/codec policy, and record links should either be cryptographically verified under their actual codec/hash or rejected. The [AT Protocol repository specification](https://atproto.com/specs/repository) explicitly invalidates noncompliant commit and MST links. Prior audits already recorded this hardening issue; no end-to-end signed malicious repo reproduction was built here.
2. **PLC authority metadata:** `PlcOpWitness.created_at` and `nullified` are private fields; `atproto/mod.rs:96` uses the supplied tip time for previous-key acceptance. Hypercerts does not bind a canonical PLC log tip/metadata source into its consumed witness. Review authority over ordering/timestamps and freshness against the [did:plc specification](https://web.plc.directory/spec/v0.1/did-plc) and design an authenticated registry/committee commitment if directory trust is intended. The source comments calling metadata "directory-attested" do not themselves authenticate it to the SNARK. This needs an old-key/recovery fixture and a complete anchor-admission trace before assigning an exploit severity.
3. **Output leaf domains:** `zk-core/src/merkle.rs:13` and `:39` encode address words and node ids in the same untagged preimage shape. Existing `audit_poc_leaf_domain` proves equality for zero-padded ids. Current hashed DID/pubkey node ids make practical cross-domain forgery require roughly a 96-bit prefix grind; this is a versioning/cryptographic design margin concern, not an immediate demonstrated attack. Before freezing a durable API, use explicit leaf domain tags or separate roots when practical.
4. **Strict EAS0 liveness:** `trustgraph-core/src/lane2.rs:216–225` makes an admitted prefix fork permanently unprovable under the existing history. `EasOffchainAnchorRegistry.anchor` checks signature/count/previous-head pointer but cannot prove payload validity or append consistency. `ANCHORER_ROLE` and host preflight are meaningful current defenses. Require a documented recovery/migration drill for compromised admission or permanently unavailable data; do not weaken the guest to silently skip nodes. Per-owner maximum 2048 append-only entries also eventually prevents further revocations unless a rotation/migration mechanism exists.
5. **Core API consistency:** use shared Binding primitives, centralized typed validation, explicit policy versions and bounded inputs. Keep compute telemetry separate from consensus outputs. Remove stale `journal-v2`, old Rule-Φ and “lane2 max age MUST be nonzero” comments from paths that now use v3/strict EAS0. Do not force large architecture changes solely for uniformity; weighted and composition isolation correctly limits vkey-change blast radius.
