# Trustgraphs v0.1.0 governance, authority and factory review

Reviewed 2026-09-05 against the current working tree. Scope: `contracts/src/{zodiac,governance,factory}`, associated registry authority resolution, signer guest/core, and relevant tests. No production source was changed. Existing frontend changes were preserved. Earlier August audit findings were checked against current implementations; the findings below concern current code, not historical already-fixed versions.

## Recommendation

Fix G-01 through G-03 before presenting the corresponding factory/signer features as ready for testnet. Decide G-04's liveness model before mainnet. G-05 is a consequential trust decision, not an outsider privilege-escalation exploit: explicitly accept and document it, or narrow the authority path before launch. The existing atomic Safe bootstrap, typed controllers, execution windows and role handoff are good foundations, but mock-heavy cross-program tests currently hide integration failures.

## G-01 — A valid no-op signer proof permanently exits singleton bootstrap

**Severity:** Medium (signer-sync availability; ordinary member governance and recovery remain available). **Confidence:** High. **Class:** implementation bug, permissionless trigger.

**Code:** `contracts/src/zodiac/SignerSyncZkModule.sol:241`, `:281`, `:293-294`; `crates/pagerank-core/src/signer.rs:129-145`, `:165-184`; `zk/operator/src/run.rs:1406-1415`; `contracts/src/factory/GovernedFactoryBase.sol:395-400`.

A new governed Safe has one owner and threshold one. The guest correctly returns the unchanged owner set when fewer than two eligible direct-vote witnesses exist. This `activity_applied=false` result is not committed in the journal. The hosted operator skips purchasing such proofs, but the permissionless contract accepts them and unconditionally sets `hasAppliedCheckpoint=true`; that same flag is passed into the next journal as `was_initialized`.

The consequence is a different selection policy: before initialization, two fresh scored members suffice; afterwards two fresh **current Safe owners** are required. If a prover submits a no-op while the Safe still has one owner, the latter condition can never hold. Later valid votes from many members cannot bootstrap automatic selection. The accepted no-op also consumes the score checkpoint, excluding a later useful proof for that checkpoint. Restoring progress requires a governance/recovery owner change or module replacement. Calling a no-op “applied” is therefore a security-relevant state transition even though `_syncOwners` makes no owner changes.

**Concrete sequence:** first score checkpoint/root lands; one member votes; a third party generates the ordinary signer guest result preserving the bootstrap owner; it submits this valid no-op proof; a second positive-score member subsequently votes; every subsequent guest run still preserves the singleton because two current owners cannot exist. The operator's early return is no defense against another prover.

**Validation:** `research/audits/2026-09-05-v0.1.0-reproductions/rust/tests/signer.rs` runs the unchanged canonical native `compute_signers` implementation with factory-admissible parameters: 1e18 scale, one seed, trust share 1e18, decay 0.8e18, 0.85 damping, tolerance 1e12, 100 iterations, two positive-score endpoints. It confirms (a) one witness produces an unchanged singleton, (b) two witnesses bootstrap two owners with `was_initialized=false`, (c) the same two-witness input preserves the singleton with `was_initialized=true`. This is native execution of the code called by the SP1 guest, **not** an SP1/SNARK verification. An isolated Foundry check separately exercises the contract's unconditional no-op initialization using the existing verifier mock: `test_Review_NoopInitializesSingleton` passed (321,749 gas).

**Recommendation:** separate “a checkpoint was consumed” from “eligible signer selection has initialized.” Commit an `activityApplied`/selection-outcome flag and require it for initializing/changing the high-water state, or make insufficient-activity inputs unprovable and keep the host no-op optimization. Avoid simply setting initialization based on any owner-set difference: a valid selection can equal the present set. Add a real guest-to-contract regression starting from the factory's one-owner bootstrap, including adversarial no-op submission. Any guest/journal change requires a fresh vkey and golden vectors.

## G-02 — Canonical Safe proxies fail the bootstrap adoption codehash test

**Severity:** Medium (targeted creation denial of service). **Confidence:** High. **Class:** deployment compatibility bug.

**Code:** `contracts/src/factory/GovernedFactoryBase.sol:210-212`, `:450-460`, `:478-479`; `foundry.toml:8-12`; Safe package dependencies and `deployments/sepolia.json`.

The wrapper derives prospective Safe addresses from the configured Safe factory's actual `proxyCreationCode()`, but accepts a predeployed bootstrap Safe only if its runtime code hash equals `keccak256(type(SafeProxy).runtimeCode)` compiled in this repo. Those are not interchangeable bytecodes. The currently referenced canonical factory `0xa6B71E26C5e0845f74c812102Ca7114b6a896AB2` is Safe 1.3.0, whereas the local dependency is 1.5.0 compiled here with solc 0.8.29/via-IR/Cancun.

A read-only `proxyRuntimeCode()` call to the actual canonical Sepolia factory returned 171 bytes and hash `0xb89c1b3bdf2cf8827818646bce9a8f6e372885f8c55e5c07acbd307cb133b000`. The local artifact is 114 bytes and hash `0x90e6ebb6f8967c87a6c36519ff6f2a6b7a4d996dc7b0d46d58eb8bf9716539ea`. Every legitimately predeployed canonical bootstrap proxy therefore fails adoption at the first check, regardless of correct singleton, owners, threshold, nonce, guard, modules and fallback handler.

**Concrete sequence:** a third party observes creator/name/salt, builds the public factory-only initializer, and calls the public canonical Safe factory for all 16 deterministic nonces. Each resulting Safe is innocuous and owned by the wrapper, but `createGovernedInstance` skips all of them and reverts `BootstrapSafeUnavailable`. Unsquatted creation works; changing the salt can evade an existing squat, but the adversary can target the next visible request. This is not Safe theft.

**Validation:** the canonical Sepolia fork reproduction passed, including an unsquatted positive control and failure after all 16 canonical bootstrap candidates were predeployed.

**Recommendation:** pin the actual audited deployed proxy runtime hash together with factory/singleton/version, or derive a reference runtime through the configured factory and verify it once. Preserve the existing full state-adoption checks. Add a fork test using the exact production Safe artifacts for both unsquatted creation and all-16 predeployment adoption. Local `new SafeProxyFactory()` tests cannot establish compatibility with canonical deployments.

**External corroboration:** the official [Safe 1.3.0 deployment registry](https://raw.githubusercontent.com/safe-global/safe-deployments/main/src/assets/v1.3.0/proxy_factory.json) identifies this factory address; [official 1.3.0 proxy source](https://raw.githubusercontent.com/safe-global/safe-smart-account/v1.3.0/contracts/proxies/GnosisSafeProxy.sol) is the older implementation. Byte lengths/hashes above are measured from RPC/local artifacts, not inferred from the registry text.

## G-03 — Weighted and composition factories can enable a signer guest that cannot prove their parameters

**Severity:** Medium (advertised feature permanently nonfunctional). **Confidence:** High. **Class:** cross-program API compatibility bug.

**Code:** `contracts/src/factory/GovernedWeightedTrustgraphsFactory.sol:57-104`; `contracts/src/factory/GovernedTrustComposeFactory.sol:56-103`; `contracts/src/factory/GovernedFactoryBase.sol:362-376`; `contracts/src/factory/InstanceDeployers.sol:216-225`; `contracts/src/zodiac/SignerSyncZkModule.sol:247`, `:276`; `zk/program/src/signer.rs:13-22`; `crates/pagerank-core/src/signer.rs:153-173`; `contracts/src/params/WeightedPriorParamsCodec.sol:27-43`; `contracts/src/params/TrustComposeParamsCodec.sol:34-56`.

Both wrappers accept `signerSync.enabled=true` and wire the same signer-sync program. That guest exclusively evaluates `pagerank_core::Params`/PageRank and commits its 17-word, version-3 parameter hash. The weighted snapshot requires a different 13-word, version-1 hash; composition requires its different 20-word, version-1 hash and a different accumulator statement. Matching either with the existing signer guest would require a hash collision/preimage. The installed verifier must reject real proofs, although the factory succeeds and emits an apparently configured owner-rotation module.

The contrast is instructive: the standard hybrid factory already rejects signer sync explicitly (`GovernedTrustgraphsFactory.sol:113`), and the deployer rejects nonzero anchor registries. The weighted/compose compatibility boundary is missing.

**Test gap:** `contracts/test/unit/factory/GovernedWeightedTrustgraphsFactory.t.sol:359-439` is called `test_CreateDiscoverAndApplyOptionalSignerSyncWithoutConfigEdit`, but the verifier at `:49-63` only compares a digest assembled by the test and the activity source is mocked. It demonstrates contract plumbing, not existence of a proof under the actual signer program.

**Recommendation:** reject signer enablement on every unsupported program now. If it is a mainnet requirement, either implement dedicated weighted/composition signer statements or redesign selection to authenticate an already accepted score snapshot (plus complete output data), with a precise checkpoint/source binding. Expose a compatibility matrix keyed by program identity and guest version, enforced on-chain. Require at least one native/SP1 execution plus genuine verifier fixture for each supported factory/guest combination.

## G-04 — Signer proving depends on a continuously moving activity head and unbounded lifetime history

**Severity:** Medium availability/design risk. **Confidence:** High for invalidation and growth; practical cost/throughput thresholds need measurement. **Class:** adversarial liveness design.

**Code:** `contracts/src/zodiac/SignerSyncZkModule.sol:250-256`; `contracts/src/zodiac/MerkleGovModule.sol:335-338`, `:641-648`, `:718-731`; `crates/pagerank-core/src/signer.rs:82-101`; `zk/operator/src/handlers.rs:651-658`.

Every direct vote changes the hash-chain head, while proof submission requires the proof's activity head/count to equal the live head/count. Any valid member's new direct vote therefore invalidates every proof currently being generated, even when it would not affect the selected signers. A member can create an empty-action proposal and vote immediately with `proposeWithVote`, so the attack does not require an existing open proposal, proposal success or a high voting share. Repeated writes faster than proving/confirmation can prevent rotations indefinitely; an attacker can also invalidate a proof in the public mempool.

Separately, every proof must replay the entire lifetime direct-vote history from zero, including votes outside the inactivity window. This input is unbounded on-chain and grows independently of the attestation input-capacity limit. Normal long-lived usage or spam eventually exceeds hosted proving budgets/capability limits. The safety rationale for a complete authenticated history is sound; tying the acceptance point to a perpetually moving tip leaves no reliable progress guarantee.

**Recommendation:** specify immutable activity/proving epochs or a bounded authenticated latest-activity state with an explicit freshness policy. Give proofs a finite stable acceptance interval; avoid allowing unrelated votes to globally invalidate them. Bound work independently from score-input capacity, and benchmark vote-history reconstruction/proving. The isolated `test_Review_NewVoteInvalidatesPreparedProof` passed (163,374 gas), confirming that one added activity record rejects the older checkpoint. Test a member voting while a proof is prepared/submitted, including empty-action proposal spam. Do not remove completeness or accept omitted activity merely to improve liveness.

## G-05 — The platform registry operator is a transitive administrator of Admin-tier child Safes

**Severity:** High impact authority assumption, not an unauthenticated exploit. **Confidence:** High. **Class:** trust/architecture decision requiring explicit acceptance.

**Code:** `contracts/src/registry/InstanceRegistry.sol:106-111`; `contracts/src/zodiac/ParentAuthorityModule.sol:95-106`, `:184-199`; `contracts/src/factory/GovernedFactoryBase.sol:88-95`, `:349-357`.

`InstanceRegistry.OPERATOR_ROLE` can repoint any parent's `paramsAuthority` to an arbitrary address. `ParentAuthorityModule` dynamically treats that address (or its `owner()`) as the parent execution authority. Admin-tier child modules have zero extra delay and arbitrary Safe calls/delegatecalls. Consequently the platform operational timelock can replace a parent's directory authority and thereby acquire direct execution over every enabled Admin child, even without owning the parent's actual Safe/controller/snapshot. The operator's own timelock still applies; the child does not add member voting or a child veto delay.

This is a materially larger privilege than “rewrite directory metadata.” It also creates coupling between parameter administration and child treasury authority: transferring only a parent's parameter controller changes who can administer children. `SubnetworkTier.Admin` is intentionally the zero/default enum value, so this is a likely path rather than an exotic custom module.

**Recommendation:** document the complete trust graph explicitly if accepted. Prefer a dedicated child-consented authority binding/controller with two-step migrations; require the incumbent parent/child authority to approve replacements instead of trusting a platform-editable directory field. Add a regression demonstrating exactly what a registry operator can and cannot do to parent and child assets. Reuse one typed resolver so `SubnetworkRegistry` and `ParentAuthorityModule` cannot drift. This is not a claim that parent admin itself, or governance changing its own modules, is unauthorized.

## Additional recommendations before ABI freeze

1. **Rehearse migration through the actual Safe.** Controllers bind their snapshot immutably (`TrustgraphsParamsController.sol:19`); signer sync has no score-snapshot replacement function; governance snapshot rebinding (`MerkleGovModule.sol:589`) does not itself install/remove snapshot hooks. Replacing a snapshot/module therefore needs an explicit atomic sequence covering controller registration, role grants/revocations, hooks, current proofs, live authority discovery and old distributor claims. Keep immutable deployments if desired; ship a tested migration recipe instead of assuming `InstanceRegistry.update` moves the instance. `authorityOf` records installation-time module addresses, not a complete live upgrade registry.
2. **Recovery should have explicit expiry/revocation semantics.** `DelayedRecoveryModule.sol:73-84` has a lower time bound but no upper bound; `setProposer` at `:97-102` preserves every old queued action. Years-old actions can execute after a proposer change. The same no-expiry pattern exists in delayed `ParentAuthorityModule` actions. This is currently authorized queued power, not a bypass. Consider an immutable execution window and a generation increment on proposer rotation, or document and test the requirement to cancel every old action/disable the old module. Never treat proposer rotation alone as revoking its scheduled capabilities.
3. **Decide whether the full signer module is worth shipping under an owner-locked Safe.** The sealed guard prevents every normal owner `execTransaction`, regardless of selected owners/threshold. Signer rotation does not improve the member-governance or recovery execution routes. Clarify the concrete identity/signature use case; defer the module if it is unnecessary for v0.1 rather than freezing a second proof protocol without an exercised consumer.
4. **Move immutable safety bounds to every mutation path.** The deployer enforces `topN <= 64`, but `SignerSyncZkModule._setSelectionParams` (`:395-410`) omits that cap. Governance can configure a far larger set and cause expensive owner diffs. Centralize selection validation and expose all selection fields, rather than only a hash plus one scalar and an event without the full replacement preimage. This is governance misconfiguration risk, not outsider access.
5. **Simplify governance proposal APIs before the first public ABI.** Consider a `ProposalAction[]` tuple instead of five parallel arrays, store a compact metadata commitment/URI instead of repeated unbounded strings, and make the immediate vote in `proposeWithVote` explicitly consistent with/documented against `votingDelay`. Retain action data needed for reliable execution, full proposal pinning, failed-action atomicity and the immutable execution window. Avoid semantics encoded only in frontend conventions.
6. **Make verification fixtures test the actual trust boundary.** Owner-diff fuzzing and malicious-verifier unit tests are valuable but insufficient for guest compatibility. Run actual guest/codec fixtures against the contract's independently reconstructed journal, plus exact canonical Safe deployment fork tests. Include authority enumeration after factory creation and after migration; assert the wrapper/deployers retain no roles or modules.
7. **Freeze a small supported-program matrix and deployment artifact set.** Bind verifier/program identity, parameter ABI version, Safe factory/singleton/proxy hashes, module implementation hash, compiler settings and chain timing defaults. The block-based member route (57,601+ blocks) must finish well within the timestamp-based 14-day veto window on every supported chain. Existing governance docs already call for this validation; automate it for the actual release profile.
8. **Reduce historical implementation commentary in production code.** Several comments describe obsolete field counts, roles or assumptions (e.g. three selection words despite five, single-lane references, “all three wrappers,” and factory directory `OPERATOR_ROLE` despite current registrar separation). Keep the invariant/rationale beside code and move audit dates, abandoned choices and indexer incident histories to design documents; correct NatSpec before tagging generated APIs.

## Positive results and limits

Atomic Safe installation seals the owner route before the creation transaction ends. Child deployers take explicit authorities and retain no created-instance privilege. The standard hybrid signer rejection, domain-bound signer journal, checkpoint-pinned score params, safe owner-diff ordering, signer pause control, and both-empty-only accumulator rotation are present. Merkle governance snapshots root, total power, quorum and execution timing; failed actions revert atomically and proposals expire. These close relevant earlier audit findings; ordinary governed Safe self-calls/module management are intentional authority, not a delegatecall exploit.

Current local build artifacts fit EIP-170 with margin: TrustgraphsFactory 21,207 bytes, GovernedTrustgraphsFactory 18,036, ContributionsFactory 17,139, GovernedTrustComposeFactory 14,609, GovernedWeightedTrustgraphsFactory 13,774, MerkleGovModule 13,653, SignerSyncZkModule 7,829. These are current artifact measurements, not a guarantee about a different release build. The helper-deployer architecture is justified by code-size constraints.

No genuine SP1 proof was generated in this subreview. Native signer reasoning and mock-verifier contract checks are explicitly separated. The canonical Safe runtime data was read from public Sepolia RPC. Parent agent owns baseline test results and release/CI/deployment verification; this review does not claim coverage of frontend/indexer or operator operations beyond the security-relevant signer no-op boundary.
